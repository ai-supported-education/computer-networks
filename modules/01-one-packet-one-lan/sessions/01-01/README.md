# 01-01 — Различить интерфейс, адреса и вложенные сообщения

Время: 40 минут.

Когда вы запускаете `ping`, терминал показывает одно действие: запрос ушёл, ответ
вернулся. В захвате сети тот же обмен выглядит сложнее — рядом оказываются имя
интерфейса, две пары адресов и несколько заголовков. Если воспринимать всё это как
один безымянный «пакет», непонятно, почему адресов несколько и к чему относится
каждое поле.

Начнём с самого короткого маршрута: один узел `alpha` отправляет Echo Request
соседнему узлу `beta`. Мы разберём уже готовую запись обмена и увидим, что
сообщение ICMP находится внутри IPv4-датаграммы, а та — внутри кадра Ethernet.
Пока не нужно знать, как система выбрала маршрут или узнала MAC-адрес получателя.

## Результат и границы

После карточки вы сможете по полям одного локального обмена отличить:

- сетевой интерфейс (`interface`) — точку, через которую система отправляет и
  принимает кадры;
- MAC-адрес — адрес доставки кадра Ethernet в пределах рассматриваемого канала;
- IPv4-адрес — адрес конечного узла внутри IPv4-датаграммы;
- сообщение ICMP Echo — запрос или ответ, вложенный в датаграмму.

В карточке рассматривается только уже подготовленная LAN с двумя узлами. Как
система вычисляет принадлежность к LAN, выбирает маршрут и узнаёт MAC соседа,
пока отложено. Это важная граница: готовый адрес в сценарии — исходный факт, а не
результат ещё не изученного алгоритма.

## Причинная модель: не «слои для запоминания», а вложенные решения

Пусть процесс на узле `alpha` просит операционную систему отправить Echo Request
узлу `beta`. Для этой задачи заранее известны интерфейс и оба набора адресов.

```text
процесс alpha создаёт
ICMP Echo Request
  ↓ сообщение становится содержимым
IPv4 datagram  src=172.30.0.10, dst=172.30.0.20
  ↓ датаграмма становится содержимым
Ethernet frame src=02:42:ac:1e:00:0a, dst=02:42:ac:1e:00:14
  ↓ внешний кадр отправляется через
интерфейс alpha → локальный канал → интерфейс beta
```

Это не четыре названия одного объекта.

1. ICMP задаёт смысл управляющего сообщения: здесь это Echo Request.
2. Заголовок IPv4 называет конечные узлы IPv4 и через `protocol number = 1`
   указывает, что внутри находится ICMP.
3. Заголовок Ethernet называет отправителя и получателя в локальном канале и через
   EtherType `0x0800` сообщает, что внутри находится IPv4.
4. Интерфейс — место отправки кадра. У него могут быть состояния и несколько
   адресов; сам интерфейс не равен ни MAC-, ни IPv4-адресу.

При приёме заголовки читаются в обратном направлении: интерфейс получает кадр,
обработчик Ethernet видит подходящий MAC-адрес назначения и EtherType, обработчик
IPv4 — адрес назначения и номер протокола, а обработчик ICMP — Echo Request.
Ответ — новое сообщение и новый кадр, а не тот же объект, «развернувшийся обратно».

### Ход одного успешного обмена

| Шаг | Где | Создано или проверено | Наблюдаемое поле |
| ---: | --- | --- | --- |
| 1 | `alpha` | ICMP Echo Request | `icmp.type = 8` |
| 2 | `alpha` | IPv4 datagram вокруг ICMP | `ip.src`, `ip.dst`, `ip.proto = 1` |
| 3 | `alpha` | Ethernet frame вокруг datagram | `eth.src`, `eth.dst`, `eth.type = 0x0800` |
| 4 | канал | кадр передан между интерфейсами | один захваченный кадр |
| 5 | `beta` | заголовки прочитаны снаружи внутрь | значения destination относятся к `beta` |
| 6 | `beta` | создан отдельный Echo Reply | `icmp.type = 0` и обратные пары адресов |

Порядок таблицы — причинная модель. Один захват рядом с `alpha` обычно показывает
кадры после их построения или до разбора; он не доказывает, какой участок кода
внутри ядра выполнился.

## Разобранный сценарий 1: Echo Request

Текстовое представление искусственного захвата из TShark содержит строку:

```text
frame=1 eth.src=02:42:ac:1e:00:0a eth.dst=02:42:ac:1e:00:14 \
eth.type=0x0800 ip.src=172.30.0.10 ip.dst=172.30.0.20 \
ip.proto=1 icmp.type=8
```

Из этой строки можно установить как факты наблюдения:

- заголовок Ethernet содержит локальные адреса source `…:0a` и destination `…:14`;
- содержимое кадра Ethernet размечено как IPv4;
- IPv4-датаграмма направлена от `.10` к `.20` и несёт ICMP;
- сообщение ICMP — Echo Request.

Можно сделать ограниченный вывод: строка согласуется с локальным Echo Request от
`alpha` к `beta`. Без отдельно заданных точки и направления захвата она не
доказывает сам момент выхода через интерфейс. Нельзя по одной строке утверждать,
что `beta` получил кадр, создал ответ или что любой другой сетевой путь исправен.

## Разобранный сценарий 2: похожий кадр, другое содержимое

```text
frame=7 eth.src=02:42:ac:1e:00:0a eth.dst=ff:ff:ff:ff:ff:ff \
eth.type=0x0806 arp.opcode=1 arp.src.proto_ipv4=172.30.0.10
```

Здесь тоже есть MAC-адреса source и destination и кадр Ethernet, но
`eth.type=0x0806`, а не `0x0800`. Поэтому внутри нет IPv4-датаграммы и поля
`ip.src`, `ip.dst`, `icmp.type` к этому кадру неприменимы. Это ARP Request; его
механизм будет разобран в `01-04`. Пока достаточно не приписывать кадру
отсутствующие заголовки.

## Факты, наблюдения и выводы

- **Исходный факт (`source fact`):** по спецификации IPv4 номер протокола `1`
  обозначает ICMP, а ICMP type `8`/`0` — Echo Request/Reply.
- **Допущение (`assumption`):** узлы в сценарии уже находятся в одной
  подготовленной LAN, а нужный destination MAC дан.
- **Наблюдение (`observed`):** конкретные поля, действительно прочитанные из строки
  или захвата.
- **Вывод (`inference`):** ограниченное объяснение, которое следует из наблюдений
  и допущений.
- **Неизвестное (`unknown`):** всё, для чего нет поля или отдельного доказательства.

Первичные источники для форматов: [RFC 792](https://www.rfc-editor.org/rfc/rfc792.html)
для ICMP и реестр EtherTypes IEEE, значения из которого отображает TShark. В
карточке не требуется читать RFC целиком.

## Два правдоподобных неверных пути

1. **«MAC — постоянный глобальный адрес компьютера, IPv4 — то же самое в другом
   виде».** Они принадлежат разным заголовкам и отвечают на разные вопросы.
   Интерфейс может сменить оба значения; маршрутизатор в будущей главе меняет
   внешнее оформление локального канала, не превращая MAC в IPv4.
2. **«Если виден Echo Request, значит `ping` успешен».** Запрос доказывает только
   своё наличие в точке захвата. Для успеха нужен отдельный Echo Reply и
   соответствие идентификаторов/полей обмена.
