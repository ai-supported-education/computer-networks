# 01-06 — Восстановить полный путь локального пакета

Время: 55 минут.

За пять карточек вы отдельно увидели интерфейс и адреса, проверили живую
лабораторию, разобрали поля кадра, сравнили cold/warm ARP и нашли границу сбоя.
Но настоящая диагностика не выдаёт эти наблюдения по темам: перед вами оказывается
одна лента событий, и связи между ними нужно восстановить самостоятельно.

В финале главы вы получите новый набор данных без готового пересказа. Нужно будет
собрать из отдельных наблюдений цельный путь: от исходного состояния интерфейса и
поиска MAC-адреса до двух пар Echo Request/Reply. Это не экзамен на память — все
утверждения по-прежнему должны опираться на конкретные поля и ссылки.

## Результат и границы

Вы получите новый искусственный набор доказательств
`fixtures/01-06/novel-local-exchange.pcap` вместе с хранящимся в репозитории
текстовым baseline и восстановите причинный путь обмена в `packet-path.md`: от
исходного состояния интерфейса через доставку на канальном уровне и данные о
соседе до сообщений IPv4/ICMP и обратно.

Это интеграция главы, а не проверка памяти на названия. Для каждого шага нужно
показать доказательство и классифицировать утверждение как `source fact`,
`assumption`, `Observed`, `Inference` или `Unknown`. Вычисления CIDR, gateway и
route lookup остаются за пределами; данное в provenance допущение «одна LAN» не
превращается в универсальный вывод.

## Модель полного отчёта

Хороший отчёт о пути пакета отвечает на пять разных вопросов:

| Вопрос | Тип ответа | Пример допустимого доказательства |
| --- | --- | --- |
| Что было задано до запуска? | source fact / assumption | inventory, provenance |
| Что реально было видно? | Observed | поле кадра, снимок кэша соседей |
| Как кадры связаны во времени? | Observed + порядок | номера кадров/отметки времени |
| Что из этого следует? | Inference | переход этапа со ссылками на Observations |
| Чего захват не показывает? | Unknown | обработка внутри узла, причины задержки |

Путь удобно собирать не сверху вниз по «слоям OSI», а по решениям:

```text
запрошен локальный обмен
  → есть данные об интерфейсе source
  → канальный адрес назначения уже известен или найден
  → наблюдались события доставки Ethernet
  → прочитаны IPv4-поля узлов
  → сопоставлены ICMP Request/Reply
  → на source наблюдался ответ
```

Один кадр может одновременно доказывать наличие нескольких вложенных сообщений,
но одно поле не доказывает соседний этап. Например, `icmp.type=0` сообщает тип
сообщения; связь с конкретным Request требует адресов, Echo identifiers и
контекста payload.

## Разобранный сценарий 1: полный cold-обмен

Последовательность искусственного примера (не целевой fixture):

```text
t0 neighbor .20 absent
t1 ARP request: broadcast, asks for .20
t2 ARP reply: .20 reports MAC …:14
t3 IPv4/ICMP request: .10 → .20, type 8
t4 IPv4/ICMP reply:   .20 → .10, type 0
t5 neighbor .20 at …:14 present
```

`Observed` t1–t2 вместе со снимками объясняют появление соответствия. `Observed`
t3–t4 доказывают Request/Reply в точке захвата. Ограниченный `Inference`: набор
согласуется с успешным локальным Echo-обменом после разрешения адреса соседа.
`Unknown`: какие функции ядра выполнялись, почему обмен занял конкретное время и
терялись ли кадры вне ограниченного окна.

## Разобранный сценарий 2: внешне похожий, но неполный путь

```text
t0 neighbor .20 absent
t1 ARP request for .20
t2 ARP reply for .20
t3 ICMP Echo Request .10 → .20
-- capture ends --
```

Здесь канальный адрес разрешён и Request отправлен, но полный обмен не доказан.
Нельзя нарисовать обратную стрелку только потому, что типичный `ping` должен иметь
Reply. `Expected` и `Observed` остаются разными.

## Две типичные ошибки

1. **Пересказать захват строками без причинных связей.** Список полей полезен, но
   не объясняет, какой предыдущий факт сделал возможным следующее событие и где
   ограничен `Inference`.
2. **Заполнить пропуски «нормальным поведением сети».** Если в наборе нет
   доказательств выбора маршрута, внутренней работы процесса или доставки за
   пределами точки захвата, эти элементы должны остаться `Assumption`/`Unknown`,
   даже если схема кажется незавершённой.

## Процедура

1. Выполните `pnpm network:fixture preflight`. Продолжайте только после PASS для
   локального `unix://` endpoint и закреплённого образа. Если не хватает только
   образа, выполните `pnpm network:fixture preload` и повторите preflight.
2. До `inspect` отделите в `packet-path.md` заданное от предполагаемого. В
   `Fixture identity and provenance` и `Source facts` укажите путь, SHA-256,
   искусственное происхождение и versioned baseline из файлов fixture. В
   `Assumptions` запишите предоставленное допущение об одной LAN. Затем в
   `Expected before action` поставьте отметку времени командой
   `node -e 'console.log(new Date().toISOString())'` и предскажите только форму
   ограниченного доказательства. Поля целевого fixture не становятся `Observed`,
   пока вы не прочитали фактический вывод инспектора.
3. Проверьте identity и provenance, затем получите нормализованное представление
   офлайн:

   ```bash
   pnpm network:fixture verify fixtures/01-06/novel-local-exchange.pcap
   pnpm network:fixture inspect fixtures/01-06/novel-local-exchange.pcap
   ```

   `inspect` создаёт уникальную директорию `.training/evidence/01-06/<run-id>/` с
   `preflight.txt`, `events.jsonl`, `inspect.txt` и `post-check.txt`. Остановитесь
   при несовпадении hash, неизвестном происхождении, неожиданном доступе к сети,
   очистке без `exact_container_absent=true` или расхождении исходного файла с
   текстовым представлением. Fixture не изменяйте. При ошибке очистки используйте
   только напечатанную команду с директорией неудачного запуска. Перед удалением
   она сверит Docker endpoint, Engine ID, зарезервированные имя и роль, run label
   и container ID, а после — ограниченное время проверит, что чистое состояние
   сохраняется:

   ```bash
   pnpm network:fixture cleanup .training/evidence/01-06/<failed-run-id>
   pnpm network:lab status
   ```

   Не используйте команды широкой очистки Docker.
4. Перенесите в `Inspector action and raw evidence` один путь запуска, отметку
   времени действия из `events.jsonl` и полный набор ссылок на исходные данные.
   Ссылки на текстовое представление оформляйте как `path:line`; ссылки на кадры —
   как `inspect.txt`, `frame.number=N` и точное `field=value`, чтобы было ясно,
   какое `Observation` поддерживает стрелку.
5. Не заглядывая в hints/solution, составьте в `packet-path.md` список всех
   кадров: номер и относительный порядок; поля `src`/`dst`/`type` Ethernet; поля
   адресов и протокола IPv4 либо поля ARP; для ICMP — `icmp.type`, `icmp.ident` и
   `icmp.seq` там, где они действительно присутствуют.
6. В секции `Echo pair correlation` самостоятельно найдите все ICMP Echo-кадры и
   объедините каждый Request с соответствующим Reply. Не опирайтесь только на
   соседство или порядок. Для каждого найденного Echo-кадра перенесите из
   исходного `inspect.txt` одну строку точного формата; число строк и номера кадров
   определите по собственному наблюдению:

   ```text
   echo_frame=<observed frame number> eth.src=<observed> eth.dst=<observed> ip.src=<observed> ip.dst=<observed> icmp.type=<observed> icmp.ident=<observed> icmp.seq=<observed>
   ```

   Затем явно перечислите найденные пары и объясните каждое сопоставление. Внутри
   доказанной пары `icmp.ident` и `icmp.seq` должны совпасть, значения
   `eth.src/eth.dst` и `ip.src/ip.dst` — развернуться, а `icmp.type` — различать
   Request и Reply. Если пар несколько, покажите, какое наблюдаемое поле не даёт
   смешать два обмена.
7. Сгруппируйте кадры в причинные этапы. Для каждой стрелки укажите процитированное
   `Observation`; совпавший порядок сам по себе не доказывает внутреннюю причину.
8. Заполните таблицу происхождения утверждений (`epistemic ledger`):
   - `Source facts`;
   - `Assumptions`;
   - `Observations`;
   - `Inferences`;
   - минимум три `Unknowns`.
9. Дайте итог одной фразой, область применимости и один проверочный контрсценарий
   (`counterfactual`): какое конкретное изменение доказательств опровергло бы ваш
   основной `Inference`.

Живая топология не создаётся, но офлайн-инспектор использует временный контейнер.
Из `post-check.txt` того же запуска перенесите `checked_at`,
`exact_container_absent=true` и нулевые счётчики ресурсов с метками курса, затем
проверьте состояние:

```bash
pnpm network:lab status
```

## Проверка и доказательства

- Локально: `network-evidence` проверяет identity fixture, один запуск с исходными
  данными, порядок Expected/action/cleanup, список всех кадров и точные поля Echo
  относительно нормализованного fixture в репозитории. Он проверяет найденные
  Request/Reply-пары по identifier/sequence и обратным адресам, обязательные секции и ссылки на
  исходные данные, признак очистки и отсутствие TODO. Корректность остальных
  причинных стрелок, таблицы утверждений и counterfactual проверяет агент.
- Практически: относящийся к запуску `inspect.txt` сохраняет method и фактическое
  чтение искусственного pcap из репозитория; `post-check.txt` доказывает cleanup
  того же запуска.
- Агент: проверяет причинную связность, соответствие полей, категории утверждений,
  counterfactual и соблюдение границы главы.
- Доказательство: `packet-path.md`.
